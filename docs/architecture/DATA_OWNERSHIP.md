# Workline Data Ownership & Storage Boundaries

**Audit Date**: 2026-08-23  

---

## 1. Domain Data Ownership Model

| Data Domain | Owning Service | Primary Data Store | Access Pattern |
| :--- | :--- | :--- | :--- |
| **User & Team Identity** | **R1 CORE** | Clerk + SQLite (`user_storage.db`) | Read on edge / Mutate via R1 Auth APIs |
| **Project Workspace State** | **R1 CORE** | SQLite (`user_storage.db`) + Signed `.wlipjt` | Project archive packaging & signing |
| **Research Logs & Traces** | **R2 AI** | Ephemeral memory + R3 Vector Store | Stored in Qdrant for semantic recall |
| **Knowledge Graph & Schemas** | **R3 KNOWLEDGE** | **SurrealDB** (`:8000`) | Graph queries via R3 Internal API |
| **Vector Embeddings & Chunks**| **R3 KNOWLEDGE** | **Qdrant** (`:6333`) | Dense vector similarity queries via R3 |
| **DRC Constraints & Rules** | **R4 ENGINEERING**| Structured JSON rules / Schemas | Evaluated in memory; persisted in `.wlipjt` |
| **PINN Surrogates & Residuals**| **R4 ENGINEERING**| ONNX neural weight files | In-memory inference; output to response |
| **BOM & Vendor Catalog** | **R5 PROCUREMENT**| Supplier REST API cache | Query supplier prices; generate line items |
| **x402 Payment & Orders** | **R5 PROCUREMENT**| Order records / On-chain hash | Signed order state and transaction receipts |

---

## 2. Invariant Rules of Data Governance

1. **No Shared Database Mutexes**: R2, R4, and R5 MUST NOT directly write to SurrealDB or Qdrant without calling R3 Knowledge APIs.
2. **Explicit Contracts**: All cross-service state mutations must use validated Pydantic DTOs over HTTPS/JSON.
3. **Cryptographic Provenance**: Any engineering release package (`.wlipjt`) generated by R4 or R5 must be finalized and signed through R1 Project Packaging.
